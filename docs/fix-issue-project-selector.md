# vs-redmine-client プロジェクト変更不具合 修正指示

## 目的

GitHub リポジトリ `tiohsa/vs-redmine-client` において、プロジェクトを変更しても選択したプロジェクトへ正常に切り替わらない、または一度切り替わった後に以前のプロジェクトへ戻る不具合を修正する。

対象リポジトリ:

* `https://github.com/tiohsa/vs-redmine-client`

最新のデフォルトブランチを基準に調査・修正すること。

---

## 既知の問題

静的調査では、以下の競合が疑われている。

### 1. `Redmine: Select Project` コマンドの二重ロード

コマンド側で以下のような処理が行われている可能性がある。

```ts
ticketsPresentation.setSelectedProjectId(numericId);
ticketsPresentation.refresh();
```

一方、`setSelectedProjectId()` の内部でもプロジェクト保存後にチケット一覧を再取得している。

そのため、次の処理が並行して実行される可能性がある。

1. 新しいプロジェクトの選択処理を開始
2. 選択処理の完了を待たずに `refresh()` を実行
3. 古いプロジェクトIDでチケット取得を開始
4. 新しいプロジェクトIDで別のチケット取得を開始
5. APIの応答順によって古い結果が最後に画面へ反映される

### 2. 古いAPIレスポンスが最新状態を上書きする

`loadTickets()` が複数回並行実行された場合、開始時に取得したプロジェクトIDの結果を、現在の選択状態を確認せずに反映している可能性がある。

例:

```text
プロジェクトAの取得開始
プロジェクトBへ変更
プロジェクトBの取得開始
Bの取得完了 → Bを表示
Aの取得完了 → Aの結果で上書き
```

### 3. プロジェクト選択状態をVS Code設定から毎回読み直している

選択中プロジェクトを実行時状態として保持せず、以下の設定値をリアルタイムな正本として使用している可能性がある。

* `redmine-client.selectedProjectId`
* `redmine-client.selectedProjectName`

IDと名前が別々に保存されるため、中間状態や保存遅延の影響を受ける可能性がある。

* プロジェクト選択ドロップダウンのイベント処理
* `project.select` メッセージの送信・検証・受信
* `DashboardController.selectProject`

## 必須修正方針

### A. プロジェクト変更処理を単一の非同期処理に統一する

プロジェクト選択処理は、呼び出し元から完了を待てるようにする。

望ましい形:

```ts
setSelectedProjectId(projectId: number): Promise<void>;
```

以下の階層も必要に応じて `Promise<void>` を返すようにする。

* `TicketPresentationPort`
* `DashboardWebviewProvider.selectProject`
* `DashboardController.selectProject`
* `DashboardProjectService.selectProject`

`void this.projectService.selectProject(...)` のように非同期処理を投げっぱなしにしないこと。

### B. コマンド側の重複した `refresh()` を削除する

`selectProject()` 内でチケット一覧を再取得する設計であれば、コマンド側から追加の `refresh()` を実行しないこと。

修正後の意図:

```ts
await ticketsPresentation.setSelectedProjectId(numericId);
```

同じプロジェクト変更に対して、チケット取得処理を二重実行しないこと。

### C. 古いチケット取得結果を破棄する

`loadTickets()` に最新リクエスト判定を導入すること。

推奨方式:

* generation counter
* request sequence ID
* `AbortController`
* 上記の組み合わせ

最小実装例:

```ts
private ticketLoadGeneration = 0;

async loadTickets(): Promise<void> {
  const generation = ++this.ticketLoadGeneration;
  const project = this.deps.getResolvedProject();

  const result = await this.listIssues(...);

  if (generation !== this.ticketLoadGeneration) {
    return;
  }

  // 最新リクエストだけを反映
}
```

ただし、成功結果だけでなく以下にも同じ判定を適用すること。

* `loading = false`
* エラー状態
* チケット件数
* フィルタ候補
* 未同期状態の更新
* 選択チケットの更新

古いリクエストの成功・失敗が最新画面を上書きしてはならない。

### D. 実行時の選択状態と永続化を分離する

現在選択中のプロジェクトは、DashboardまたはProjectServiceのメモリ状態を正本とする。

VS Code設定は、再起動後の復元用の永続化先として扱うこと。

推奨動作:

1. 選択対象のプロジェクトを検証
2. 実行時の選択状態を更新
3. Dashboard state を更新
4. 旧チケット状態をクリア
5. 設定へ永続化
6. 新プロジェクトのチケットを取得

設定保存が完了するまで、旧プロジェクトを現在値として参照し続ける設計にしないこと。

ただし、変更範囲が過大になる場合は、最低限以下を保証すること。

* プロジェクト変更処理中に旧設定値を読み直さない
* 同一処理内で確定したプロジェクトIDをチケット取得へ渡す
* 設定保存遅延が表示結果に影響しない

### E. プロジェクト変更時に依存状態をリセットする

プロジェクト変更時に、少なくとも以下をクリアすること。

* チケット一覧
* 総チケット件数
* 選択チケットID
* 選択チケット詳細
* チケット詳細パネル
* コメント一覧
* コメント対象チケットID
* 編集用メタデータ候補
* 新規作成・詳細表示など、旧プロジェクトに依存する作業パネル

プロジェクト変更直後に、旧プロジェクトの詳細やコメントが残らないこと。

## プロジェクトIDの検証

コマンドパレットから数値IDを指定した場合、プロジェクト一覧に存在しないIDを無条件で保存しないこと。

少なくとも以下のいずれかを実施する。

### 推奨

取得済みプロジェクト一覧から選択させる `QuickPick` に変更する。

表示例:

```text
Project Name
identifier / ID: 123
```

### 代替

入力された数値IDが取得済みプロジェクト一覧に存在することを確認する。

存在しない場合:

* 現在の選択状態を変更しない
* 明確なエラーを表示する
* チケット取得を実行しない

---

## エラー処理

プロジェクト変更に失敗した場合の状態を明確にすること。

### 設定保存失敗

以下のどちらかに統一する。

1. 画面上の選択をロールバックする
2. 実行時選択は維持し、永続化失敗を警告する

推奨は2。ただし再起動後には復元されないことをユーザーへ通知する。

### チケット取得失敗

* 選択したプロジェクト自体は維持する
* 旧プロジェクトのチケットは再表示しない
* 対象プロジェクトの読込エラーとして表示する
* 再試行可能にする

---

## 必須テスト

既存のテスト方式に合わせて、自動テストを追加または修正すること。

### 正常系

1. AからBへ変更するとBのチケットが表示される
2. プロジェクト選択が設定へ保存される
3. VS Code再起動相当の初期化で最後の選択が復元される
4. コマンドパレット経由でもプロジェクト変更が1回だけ実行される
5. Dashboardドロップダウン経由でも正常に変更できる

### 競合系

1. Aの取得中にBへ変更する
2. Bのレスポンスを先に返す
3. Aのレスポンスを後から返す
4. 最終表示がBのままであることを確認する

追加で以下も確認する。

```text
A → B → C
```

API応答順が以下でも、最終表示はCであること。

```text
C → A → B
```

### エラー系

1. 古いリクエストがエラーになっても最新表示へエラーを出さない
2. 最新リクエストが失敗した場合だけエラーを表示する
3. 存在しないプロジェクトIDでは選択状態を変更しない
4. 設定保存失敗時の仕様どおりに動作する

### 状態リセット

プロジェクト変更後に以下が残っていないこと。

* 旧プロジェクトの選択チケット
* 旧コメント
* 旧詳細パネル
* 旧編集メタデータ
* 旧チケット件数

---

## 回帰確認

以下の機能を壊していないことを確認する。

* 子プロジェクトを含める設定
* チケットの追加読込
* 全プロジェクト検索
* チケット選択
* コメント表示
* 新規チケット作成
* 子チケット作成
* チケット編集
* 未同期キュー
* プロジェクト選択の再起動後復元
* `Refresh Projects`
* `Refresh Tickets`
* `Reload Project`

特に、通常のチケット再読込とプロジェクト変更時の読込で、generation管理が競合しないことを確認する。

## 実装上の注意

* 不具合修正に必要な範囲を超えた大規模リファクタリングは行わない
* 型安全性を維持する
* `void` による非同期処理の握り潰しを避ける
* エラーを空の `catch` で隠さない
* UI側だけで状態を補正せず、Extension側の状態管理を修正する
* API応答順に依存しない実装にする
* テストのためだけの本番コード分岐を追加しない
* 既存の命名規則、責務分離、テスト構成に従う
* コメントは処理内容ではなく、競合対策の理由が必要な箇所に限定する

---

## 完了条件

以下をすべて満たした場合に完了とする。

* プロジェクト変更がDashboardとコマンドパレットの両方で機能する
* プロジェクト変更時のチケット取得が重複しない
* 古いAPIレスポンスが最新状態を上書きしない
* プロジェクト変更時に旧プロジェクトの状態が残らない
* 選択状態が適切に永続化される
* 競合テストが追加されている
* 既存テストが成功する
* lint、test、buildが成功する

実行すること:

```bash
pnpm run lint
pnpm test
pnpm run package
```

リポジトリで実際に定義されているスクリプト名が異なる場合は、`package.json` に従って実行すること。

修正後、以下の形式で簡潔に報告すること。

```markdown

## Changes

- 各変更の目的

## Concurrency Control

- 古いレスポンスをどのように破棄したか
- loading/error状態をどのように保護したか

## Tests

- 追加・修正したテスト
- 競合の再現方法

## Compatibility

- 回帰確認した機能

- 手動確認が必要な項目
```

根本原因が事前調査と異なった場合は、事前調査に合わせて実装せず、コードとテストで確認できた実際の原因に基づいて修正すること。
