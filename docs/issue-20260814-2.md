# `vs-redmine-client` 同期ライフサイクル統合・非局所的変更仕様書

## 1. 目的

本変更の目的は、`fix-bugs` で確認された個別不具合を症状単位で修正することではない。

以下を同時に説明する共通原因を閉じる。

* `createTicketFromEditor()` が production code から test fixture を参照し、`Task / Normal / In Progress / 2025-12-31` を生成データへ混入させる。
* 同コマンドで取得した attachment upload token が Ticket Create に伝播せず、添付が失われる。
* Ctrl+S `auto` モードで同期失敗・競合・`commit_unknown` 等の Outcome が presentation されない。
* 新設された generic state machine が `remote_committed -> completed` を許可し、remote read-back/local finalize を状態機械として保証できない。
* generic `UnifiedSyncOperation` / Repository / Handler を追加した一方で、実際の Ticket は `TicketSyncService`、Comment は `SyncEngine`、永続状態は `offlineSyncStore` の既存 lifecycle を引き続き使用している。
* `phase` と primary `DurableSyncEffect` が同じ remote mutation の状態を二重に保持している。
* `revision` がユーザー編集世代と永続化競合検出の双方に近い役割を持ち、新設 `persistenceVersion` も converter で毎回 `1` になる。

根本目的は、添付プロンプトが要求する通り、**同じ原因による不具合が別 entry point で再発しない構造へ変更すること**である。

変更後は次を成立させる。

> **Redmine への同期は、一つの authoritative `SyncOperation`、一つの State Machine、一つの Coordinator、一つの Repository 契約を通過する。Ticket / NewTicket / Comment の差は Handler 内の domain-specific 処理だけに限定する。**

# 3. 現状

## 3.1 確定事項

### C-01: Ctrl+S auto/manual の基本動作は改善されている

README は Existing Ticket について、

* `auto`: 保存時即時送信
* `manual`: Unsynced へ queue

を仕様としている。

`fix-bugs` では `performSyncOnSave()` が queue 後に `syncEngine.syncOne()` を呼ぶよう変更され、manual/auto の regression test も追加されている。New Ticket Draft は `auto` でも Ctrl+S では create せず queueOnly とするテストも存在する。

この仕様は維持する。

---

### C-02: `createTicketFromEditor()` に test fixture が侵入している

production command が、

```ts
import { buildIssueMetadataFixture }
  from "../test/helpers/ticketMetadataFixtures";
```

を参照している。さらに attachment を先に upload した後、`uploads` を同期へ渡さず `TicketSyncService.syncEditor()` を呼ぶ。

fixture は、

```text
tracker  = Task
priority = Normal
status   = In Progress
due_date = 2025-12-31
```

を返す。

したがってこれは単なる test smell ではなく、production input contract の破損である。

---

### C-03: attachment remote mutation が durable operation より前に存在する

`createTicketFromEditor()` は `uploadFileAttachment()` / `uploadClipboardImage()` を command 内で実行する。

この時点では Ticket の durable sync lifecycle に入っていない。

その後取得した upload token も Ticket create へ伝播していない。

これは、

```text
Entry Point
 ├─ remote side effect
 ├─ editor mutation
 └─ SyncService
```

という責務逆転を示す。

---

### C-04: auto sync の Outcome が一部捨てられる

`syncIfAuto()` は、

```text
completed
no_change
```

のみを処理し、

```text
conflict
commit_unknown
remote_committed
failed_before_commit
```

を presentation しない。例外も catch 後に通知しない。

したがって queue 成功通知後の auto sync 失敗がユーザーから見えなくなる経路が成立する。

---

### C-05: Ticket と Comment が別 orchestration を持つ

`SyncEngine` は Ticket を `TicketSyncService` に委譲する一方、Comment については、

* single-flight
* scope validation
* phase 判定
* `commit_unknown`
* remote-write checkpoint
* reconcile
* local finalization
* completion

を独自実装している。

一方 `TicketSyncService` 自身も、

* journal
* phase transition
* single-flight
* recovery
* create/update
* effects
* reconcile/finalize

を持つ。

これは意味的に同じ durable Saga lifecycle の二重実装である。

---

### C-06: 新 generic architecture は authoritative path になっていない

新たに、

* `syncOperationTypes.ts`
* `syncStateMachine.ts`
* `syncRepository.ts`
* `operationHandlers.ts`

が追加された。

しかし `syncRepository.ts` は既存 `offlineSyncStore` の型を generic DTO に変換する adapter に留まり、実 persistence owner にはなっていない。

`OperationHandler` も interface であり、既存の `views/ticketSync/*` / `commentSaveSync` を直接 import している。

完成した architecture ではない。

---

### C-07: generic State Machine が local finalize を必須化していない

現在、

```text
remote_committed
  -> complete

reconciliation_pending
  -> complete
```

が合法である。

このため、

```text
remote commit
   ↓
completed
```

とし、canonical read-back / local finalize を迂回できる。

既存テストは正常経路では `local_finalize_pending` を通しているものの、この2つの禁止遷移を直接検証していない。

---

### C-08: authoritative state が重複している

`offlineSyncStore` には、

* `phase`
* operation `revision`
* primary `DurableSyncEffect`
* `effects[]`
* `createdIssueId`
* `createdChildIds`
* `nextIntent`

等が同時存在する。

さらに `SyncOperation` と Ticket/NewTicket/Comment payload が別々に存在し、primary remote mutation 用 effect まで生成している。

つまり primary remote mutation について、

```text
operation.phase
        +
primary DurableSyncEffect.state
```

の二つの状態表現が存在する。

---

### C-09: generic operation の型安全性が不足している

`UnifiedSyncOperation` は、

```ts
payload?: any;
nextIntent?: any;
```

を持ち、remote identity も Ticket/Create/Comment 固有性に関係なく optional field で表現している。

また repository converter は全 operation を、

```ts
persistenceVersion: 1
```

として生成する。

よってこの値は現状 CAS version として信用できない。

---

### C-10: CI は HEAD を検証していない

`fix-bugs` HEAD に対応する workflow run / status は存在しない。

CI workflow は、

```yaml
push:
  branches: [main]
pull_request:
```

なので、`fix-bugs` への push だけでは実行されない。

したがって HEAD の full CI pass は未証明である。

## 4.2 異常系

* remote write 前の確定失敗 → retry可能な queued または `failed_before_commit`
* write request dispatch 後の結果不明 → `commit_unknown`
* `commit_unknown` → **自動再送禁止**

* newer local source → stale remote result で上書きしない

* compensation結果不明 → recovery required

# 5. 根本原因

## 症状群

```text
test fixture混入
attachment欠落
auto failure silent
Ticket/Comment lifecycle差異
generic state-machineの迂回可能性
persistenceVersion不成立
phase/effect二重管理
```

↓

## 直接原因

* 各 Entry Point が独自に data preparation を持つ。
* 各 Entry Point が Outcome interpretation を持つ。
* Ticket / Comment が独自 orchestrator を持つ。
* State transition owner が複数存在する。
* persistence model と application model が重複している。

↓

## 設計上の原因

**同期 Operation に authoritative contract と lifecycle owner が存在しない。**

↓

# 根本原因

> **User Intent の生成、Durable State、Remote Mutation、Recovery、Local Finalize、Outcome Presentation が単一の同期境界として定義されていない。**

これにより各入口が「必要な処理の一部」を再構成しなければならず、入口追加・変更のたびに parity bug が発生する。

添付プロンプトが警告する「症状A→関数A修正、症状B→関数B修正」で終わらせてはいけない典型ケースである。

# 8. 設計方針

## 8.1 authoritative model

同期状態の source of truth は `SyncOperation` のみにする。

概念例:

```ts
type SyncOperation =
  | TicketCreateOperation
  | TicketUpdateOperation
  | CommentCreateOperation
  | CommentUpdateOperation;
```

共通部分:

```ts
interface BaseSyncOperation<I extends SyncIntent> {
  operationId: string;
  key: SyncKey;
  connectionScope: string;

  intentRevision: number;
  version: number;

  intent: I;
  nextIntent?: I;

  state: SyncOperationState;
  effects: SecondarySyncEffect[];

  createdAt: number;
  updatedAt: number;
}
```

---

## 8.2 `revision` を二つに分離する

### `intentRevision`

ユーザー編集の世代。

### `version`

Repository mutation の CAS version。

次を禁止する。

```text
revision = user edit generation
         + persistence mutation generation
```

---

## 8.3 type-specific Intent

`any` を使用しない。

```ts
type SyncIntent =
  | TicketCreateIntent
  | TicketUpdateIntent
  | CommentCreateIntent
  | CommentUpdateIntent;
```

各 Intent は、**同期開始後に mutable Editor を読み直さなくても処理を再開できる immutable snapshot** を保持する。

---

## 8.4 operation identity

* `operationId`: 一つの remote mutation generation を識別する immutable ID
* `SyncKey`: Ticket/document/comment 等の論理対象を識別

remote write 開始前の queued Intent 更新は同 operation の `intentRevision` を更新できる。

remote write 開始後の新編集は `nextIntent` とする。

current operation completion 後は **新 operationId を持つ次世代 operation** として昇格する。

# 12. API / DTO契約

## `SyncOutcome`

Ticket / Comment 共通にする。

概念例:

```ts
type SyncOutcome =
  | { kind: "completed"; entity: SyncEntityIdentity }
  | { kind: "queued" }
  | { kind: "no_change" }
  | { kind: "conflict"; conflict: ConflictInfo }
  | {
      kind: "recovery_required";
      reason:
        | "commit_unknown"
        | "remote_reconcile"
        | "local_finalize"
        | "compensation_unknown"
        | "effect_unknown";
      remoteCommitted: boolean;
    }
  | {
      kind: "failed_before_commit";
      error: SyncError;
    };
```

`TicketSyncOutcome` と `CommentSyncOutcome` を最終的に廃止する。

現在 `SyncEngine` が別 `CommentSyncOutcome` を定義している構造は完成時に残さない。

---

## Outcome Presenter

Outcome → UI policy は一箇所へ集約する。

| Outcome              | Presentation                    |
| -------------------- | ------------------------------- |
| completed            | success + relevant view refresh |
| queued               | Unsynced refresh                |
| no_change            | 原則通知なし                          |
| conflict             | conflict workflow               |
| commit_unknown       | recovery-required warning       |
| remote_reconcile     | recovery pending                |
| local_finalize       | local recovery pending          |
| failed_before_commit | error                           |

`saveSyncExecutor.syncIfAuto()` に独自判定を残さない。

# 13. Data / Persistence

## DB

DB変更なし。

## Memento

現状 serialized queue は `operations` を source of truth とする migration 機構を既に持つ一方、application 側では Ticket/NewTicket/Comment の別 payload が存続している。

次期 schema では serialized form 自体を authoritative `SyncOperation` に統一する。

### Migration

既存 v2/v3 等の queue を、

```text
OfflineTicketUpdate
OfflineNewTicket
OfflineCommentUpdate
SyncOperation
```

から新 discriminated operation へ一度だけ変換する。

version番号自体は実装時に現在schemaを確認して決定する。

### migration要件

* queued を保持
* `remote_write_started` → `commit_unknown`
* `commit_unknown` 保持
* remote identity 保持
* child effect 保持
* compensation state 保持
* `nextIntent` 保持
* `connectionScope` 保持
* documentUri 保持
* migration失敗時に元snapshotを破棄しない

# 14. Performance仕様

本変更で同期の correctness を理由に無制限な処理増加を許可しない。

### PF-01 Remote mutation

同一 `operationId` について primary remote mutation の concurrent count:

**最大1**

### PF-02 Automatic retry

remote request dispatch 後、結果不明となった mutation の automatic retry:

**0回**

### PF-03 Normal remote write

正常な一回の sync generation について primary create/update:

**最大1回**

### PF-04 Remote read-back

通常成功経路の canonical read-back:

**原則1回以下**

追加 read-back が必要な場合は recovery attempt として明示する。

### PF-05 Intent growth

同じ SyncKey の in-flight generation:

```text
current Intent
+
nextIntent
```

を上限とし、保存回数ごとに queue entry を追加しない。

### PF-06 Request timeout

既存 `requestTimeoutMs=30000` を維持し、本architecture変更を理由に増大させない。README上の既定値も30,000msである。

### PF-07 Complexity

Queue operations/storage は operation件数 `N` に対して **O(N)** を上限とする。

# 15. Security / Permission

* API key は引き続き SecretStorage。
* `connectionScope` を operation 作成時に固定する。
* remote execution 前に必ず operation scope と current execution scope を比較する。
* Entry Point が外部から別scopeを注入して operation scope を上書きできないようにする。
* Permission error が remote commit 前に確定した場合のみ `failed_before_commit`。
* secret/API key を persisted SyncIntent に含めない。
* error/output に API key を含めない。
* attachment local source の保存場所に不要な秘密情報を記録しない。

# 23. リリース不可条件

次の一つでも成立する場合、**merge / release不可**。

1. production code が `src/test/**` を importしている。
2. attachment が Entry Point でremote uploadされた後、operation contractから外れる。
3. `commit_unknown` を通常syncが再送できる。
4. `remote_committed -> completed` が可能。
5. local finalize前に completed になれる。
6. Ticket / Comment が別 lifecycle transitionを所有する。
7. primary remote mutationがOperationとeffectの二重source-of-truth。
8. Repository CASが実効性を持たない。
9. scope mismatch operationを送信できる。
10. existing Unsynced dataをmigrationで失う。
11. auto sync failure Outcomeがpresentationされない。
12. checkpoint crash testでremote mutationが重複する。
    13.新旧sync architectureがproduction経路に共存する。
13. P0/P1が残る。
14. HEAD full CIが未実行または失敗。

# 24. 決定記録

## D-01: Sync lifecycleを一つへ統合する

**決定:** 案Dを採用。

**理由:** Ticket/Create/Commentで発生している不整合を共通原因から閉じられる最小範囲だから。

**却下:** 症状単位修正、Extension全面再設計。

**リスク:** migration規模が大きい。

**軽減:** Handler単位でbranch内段階移行し、各段階でparity test。

**再検討条件:** 単一 Coordinator が現行 Redmine operation のいずれかを表現不能とコード上で証明された場合のみ。

---

## D-02: primary remote mutationをeffectから除外する

**決定:** primary Ticket/Comment mutation の状態は `SyncOperation.state` のみに保持する。

`effects[]` は、

* child create
* attachment upload
* compensation等

の secondary Saga 用とする。

**理由:** phase/effect二重source-of-truthを除去する。

**再検討条件:** primary mutationをsecondary effectsと同一集合に置かなければ recovery invariant を実現不能と証明された場合。

---

## D-03: attachmentもdurable boundary内へ入れる

**決定:** commandからremote uploadしない。

**理由:** 現在の attachment欠落と、remote side effectのjournal外実行を同時に解消する。

**リスク:** attachment recovery設計が必要。

**軽減:** `attachment_upload` を secondary effect として扱う。

---

## D-04: `intentRevision` と Repository `version` を分離

**理由:** User edit generation と CAS は異なる概念。

`persistenceVersion: 1` のような converter-local 値を authoritative version としない。現実装では converter が常に1を設定している。

---

## D-05: Outcome presentationを共通化

**決定:** Ctrl+S / Command / Dashboard が `SyncOutcome` を直接独自解釈しない。

**理由:** `syncIfAuto()` の silent failure の再発を構造的に禁止するため。

---

## D-06: New Ticket Draft Ctrl+S は queueOnly維持

**決定:** `offlineSyncMode=auto` でも draft保存はcreateしない。

**理由:** READMEおよび追加 regression test と一致する。

---

## D-07: 中間architectureをmainへmergeしない

**決定:** generic layerだけ追加した状態では merge しない。

**理由:** 添付プロンプトの品質ゲートが要求する「完成時に新旧経路を混在させない」に直接対応するため。

---

## 最終実装指示

実装エージェントは **F-01〜F-04を個別patchとして処理して終了してはならない**。

修正の単位を、

```text
Sync Intent
   ↓
Authoritative SyncOperation
   ↓
OperationRepository
   ↓
SyncCoordinator
   ↓
Single State Machine
   ↓
Typed OperationHandler
   ↓
Redmine / Workspace adapters
   ↓
Common SyncOutcome
   ↓
OutcomePresenter
```

とし、Ticket Create / Ticket Update / Comment Create / Comment Update の**全remote mutation entry pointをこの経路へ移行すること**。

移行完了後は旧 lifecycle owner を削除する。

完了判定は、

> 「今回見つかった4件が直った」

ではなく、

> **同じ User Intent、Remote Mutation、Recovery State、Outcome を扱う別entry pointを追加しても独自 lifecycle /独自 notification /独自 remote write を実装する必要がなく、INV-01〜INV-20がState Machine・Repository・横断Testの双方で保証されている**

こととする。
