# リモートチケット状態の同期 実装判断ログ

日付: 2026-08-09
ステータス: 記録中
プロジェクトルート: `/home/glorydays/projects/src/ts/vs-redmine-client`
参照元: ユーザー依頼および実装計画
実装対象: 新規チケット作成後と既存チケット更新同期時のRedmine詳細反映

## 依頼と参照元の要約

新規作成チケットを同期した後、Redmine側で変更されたステータスがローカルMarkdownへ反映されない問題を修正する。通常の更新処理も確認し、リモートの最新状態をローカルへ反映する。

## 記録方針

このファイルには、参照元に明記されていなかった実装中の判断、変更、妥協点、仕様解釈、未解決事項、検証上の制約を記録する。

## 判断一覧

### D-001 作成・更新後のRedmine詳細を正とする

- 種別: 解釈
- タイミング: 実装前
- 参照元に書かれていたこと: 通常同期でリモート側の最新チケット全項目をローカルへ反映する。
- 参照元に書かれていなかったこと: 作成API・更新APIのレスポンスだけでは詳細な正規化後状態を取得できない。
- 判断: 作成成功後および更新成功後に`getIssueDetail`を呼び、statusを含む最新詳細をファイルとドラフト状態へ反映する。
- 理由: Redmineのワークフローや権限によるstatusの調整を確実にローカルへ反映できるため。
- 代替案: API入力値をそのまま保存する。これは今回の不具合を再現するため採用しない。
- 影響: 同期成功時に追加のGETが発生する。ローカル表示はRedmineの実値と一致する。
- 可逆性: 高。詳細取得と反映処理を戻せば従来動作へ戻せる。
- 制約: 任意判断
- ユーザー確認: 確認済み

### D-002 リモート詳細取得失敗時は作成を失敗扱いにしない

- 種別: 妥協
- タイミング: 実装中
- 参照元に書かれていたこと: 新規作成時に最新状態を反映する。
- 参照元に書かれていなかったこと: 作成成功後の詳細GETだけが失敗した場合の扱い。
- 判断: 作成自体は成功として、入力値をフォールバックにしてファイルを書き換える。`updatedAt`は取得できた場合のみ保存する。
- 理由: 既にRedmine上に作成されたチケットを、GET失敗だけで再試行して重複作成する危険を避けるため。
- 代替案: 作成結果を失敗扱いにする。重複作成リスクが高いため採用しない。
- 影響: 一時的なGET障害時はstatus反映が次回同期・再読み込みまで遅延する。
- 可逆性: 中
- 制約: 既存の作成済みチケット保護
- ユーザー確認: 事後報告

## 変更・逸脱

- オフラインの新規チケット同期でも、作成後に取得したRedmine詳細をファイル書き換えへ渡すようにした。
- 作成後の詳細取得は失敗時にフォールバックする方針とした。作成済みチケットの重複作成を防ぐため、計画の「最新詳細を反映」は取得成功時に適用する。

## 妥協点と残課題

通常同期でローカル差分がない場合もGETを行うため、同期操作ごとのAPI呼び出し数が増える。

## 検証と制約

- 実行した検証: `pnpm run compile`、`pnpm run compile-tests`、`pnpm run lint`。
- 実行できなかった検証: CodeGraphは未初期化のため使用していない。`pnpm test`と`pnpm run test:unsafe`は、既存のVS Code Electron sandbox起動エラー（`sandbox_host_linux.cc:41`）で実行できなかった。

## 結果

作成・更新・オフライン新規同期でRedmine詳細を反映する処理と回帰テストを追加した。型チェック・lint・webpack compileは成功。VS Code統合テストのみ実行環境のsandbox制約が残る。
