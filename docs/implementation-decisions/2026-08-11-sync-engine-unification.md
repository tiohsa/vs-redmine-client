## 判断一覧

### D-001 旧キュー API は移行期間の読み取り互換に限定する

- 種別: 解釈
- タイミング: 実装前
- 参照元に書かれていたこと: 分割キューを単一の `SyncOperation` コレクションへ移行し、UI・コマンドから内部キュー構造への直接依存をなくす。
- 参照元に書かれていなかったこと: 多数の既存呼び出しとテストを一度に破壊しない API 移行方法。
- 判断: 新しいストアを唯一の書き込み経路とし、旧 API は一時的に新ストアの派生ビューを返す互換層として残す。利用箇所の移行完了後に旧 API を削除する。
- 理由: 永続データ移行と同期ライフサイクル変更を分離し、既存の UI 契約を保ったまま段階的に検証できるため。
- 代替案: 旧 API を同時に全削除する。広範な変更で不具合の原因切り分けが困難になるため採用しない。
- 影響: 内部互換層は短期間残るが、実データの正本は一つになる。
- 可逆性: 中。旧 API の削除前は容易に戻せる。
- 制約: 任意判断
- ユーザー確認: 事後報告

## 変更・逸脱

- 既存の `OfflineSyncQueue` 読み取り API と個別の書き込み API は、既存 UI・保存経路との互換のため残した。永続化の正本は v2 の `operations` 配列へ移し、新規の統合 API (`listSyncOperations`、`getSyncOperation`、`upsertSyncOperation`、`discardSyncOperation`) を追加した。
- UI 投影の全利用箇所を一度に置き換える代わりに、全件同期と単一ファイル同期を `SyncEngine` に統合した。既存キュー API は派生互換層として機能する。

## 妥協点と残課題

- `TicketSyncService` の耐障害ライフサイクルは、そのまま `SyncEngine` のチケット executor として再利用した。完全な汎用 state machine への内製化は、同じ安全性を再実装するリスクが高いため行っていない。
- コメントは既存の再試行意味論を保持し、commit unknown の対話フローを追加していない。

## 検証と制約

- 実行した検証: `pnpm run compile`、`pnpm run compile-tests`、`pnpm run lint`、`pnpm test -- --grep "syncUnsyncedFileResult|offlineSyncStore|offlineSyncResult"`。VS Code 統合テストは836件成功した。
- 実行できなかった検証: 最初の sandbox 内テストは VS Code Electron の `sandbox_host_linux.cc:41` で停止したため、同一コマンドをサンドボックス外で実行した。

## 結果

`SyncOperation` の v2 永続形式、旧キューからの読み込み移行、共通 `SyncEngine`、全件同期および単一ファイル同期のエンジン経由化を実装した。チケットの既存ライフサイクルとコメントの既存 UX を保ったまま、同期実行の入口を一つにした。
