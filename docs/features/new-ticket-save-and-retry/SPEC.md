# SPEC: 新規チケットの保存時同期と失敗後の再同期

## 1. Goal

新規チケットの Markdown 下書きを保存したとき、同期モードに従って Redmine に登録できるようにする。登録が拒否された場合は下書きと失敗理由を保持し、利用者が原因を解消してから対象のチケットを再同期できるようにする。

## 2. Non-goals / Out-of-scope

- 既存チケット・コメントの保存動作、Redmine 側の権限や API 設定の変更、全失敗項目の一括再送。
- REST API 有効化後も登録できない原因の断定。以前の作成 POST の 403 と、有効化後に新しい POST が送信されたかどうかは別々に検証する。

## 3. Acceptance Criteria

- [ ] 有効な新規下書きをオンラインで保存すると、`auto` では入力を永続化して作成 POST を 1 回送り、読み戻しとローカル確定を経て作成 ID を反映する。初回保存と確定時の文書書き換えから二重作成が発生しない。
- [ ] `manual` では保存後に未同期一覧へ表示され、添付のアップロードも作成 POST も 0 回となる。明示的に同期すると最新の保存内容で 1 件作成する。
- [ ] 作成 POST が HTTP 403 で拒否された場合は下書きと失敗理由を保持する。保存・再起動・通常の一括同期による自動再送は 0 回とし、Dashboard の Unsynced と同期トレイの対象項目に「再同期」を表示する。変更前に永続化された同じ失敗も対象に含める。
- [ ] API 設定や権限を修正した後、「再同期」を選ぶと、同じ接続先の現在の認証情報と凍結済みの作成リクエストで 1 回だけ再送する。成功時は読み戻し・ローカル確定を完了する。再度拒否された場合は最新の失敗理由と「再同期」を表示する。
- [ ] 作成 POST 前のメタデータ取得に失敗した場合も下書きを保持し、「再同期」で必要な準備から再開する。作成結果が不明な場合や作成 ID が確定済みの場合は既存の専用復旧操作を使い、通常の「再同期」で作成 POST を追加しない。
- [ ] 同一試行への「再同期」の連打・同時実行で追加の作成 POST は最大 1 回とする。失敗後の追加編集は後続の変更として保持し、再送するリクエストと区別する。

## 4. Public API / DB Schema

- 既存の Redmine API と保存済みキューを使用する。更新前に記録された失敗項目を読み込み、保存済みの操作とリクエストを照合できるものを復旧対象とする。

## 5. Constraints

- **Security**　Dashboard の操作は既存のメッセージ検証を通し、実行時に接続スコープ、対象操作、状態、世代を再照合する。認証情報・リクエスト本文・応答本文は診断に含めない。
- **同期の整合性**　作成拒否後の再送には保存済みのリクエストと添付識別情報が必要。照合できない項目には既存の手動復旧案内を表示する。Primary Operation と Primary Effect の遷移は原子的に行う。
- **[ASSUMPTION]**　今回追加する「再同期」は新規チケットを対象とする。既存の再試行条件を拡張する範囲は、作成 POST 前の失敗と、送信済みの作成 POST が 403 で拒否されたケースとする。

## 6. Required Tests

- **Unit**　同期モード・失敗段階・保存済みリクエストの有無から、保存時の送信と明示的な再同期の可否を検証する。
- **Integration / E2E**　Extension Host の実際の保存イベントから両モードの送信回数、作成 ID、残存キューを検証する。作成 POST を最初は 403、次は成功とし、再起動を挟んで Dashboard の「再同期」から完了することを確認する。再度 403 となる場合と準備段階で失敗する場合も確認する。
- **Regression**　変更前の 403 記録、重複操作、後続編集、別スコープ・旧世代、結果不明・受理済みの復旧、既存チケットとコメントの保存を対象とする。仕様反映時には [保存とオフライン同期](../offline-sync.md)、[障害復旧](../sync-recovery.md)、対応する機能検証マップを更新する。
